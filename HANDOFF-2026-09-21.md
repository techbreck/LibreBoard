## 2. Why data went missing last time — and how to avoid it

Everything measurement-related that is **not in git** lives under `build/` (gitignored): corpora,
pinned models, the ONNX Runtime AAR, the measured APK, all raw device evidence, and the shared
matrix metadata. A git-based transfer (clone/push) or a sync tool that honors `.gitignore` drops
all of it — that is almost certainly the earlier "test data missing" failure.

Additionally, the only configured git remote is `upstream` (the HeliBoard project this fork
derives from). **There is no LibreBoard origin remote**, so all LibreBoard commits exist only in
this folder's `.git`.

Two safe transfer options:

1. **Folder copy (simplest):** copy the entire project folder, including `.git/`, `build/`,
   `app/build/`, and the bundle file in §3. Do not exclude gitignored paths.
2. **Git clone + bundle:** clone/push the git history however you like, then unpack
   `libreboard-phase0-handoff-2026-09-21.tar.gz` (§3) at the repository root. It reconstructs
   every gitignored artifact needed to resume.

After either, run the verification checklist in §5.

## 7. The pending decision: low-RAM matrix leg

The third matrix environment must prove `isLowRamDevice: true` with ≤2,048 MiB. Facts established
today:

- The AVD cold-boots at its RAM floor and `ro.config.low_ram` stays empty — a natural low-RAM boot
  of any available image is not possible (confirmed again, matching the 2026-09-08 recheck in
  `docs/testing.md`).
- No product/Go low-RAM image exists in the local SDK or the SDK catalog.
- The only working mechanism: on the debuggable AOSP image,
  `adb root && adb shell setprop debug.force_low_ram true && adb shell stop && adb shell start`
  — then `ActivityManager.isLowRamDevice()` genuinely returns true and the real product policy
  engages (context model auto-disabled, CTC retained).
- **`docs/testing.md` currently forbids submitting that mode as the full Phase 0 matrix leg.**
  Choosing it requires amending that documented line with an explicit labeled exception.

Options as presented: **A** debug-forced leg with explicit labeling (unblocks pooled evaluation;
~4–6 h right-sized or ~14 h full shard on the emulator — prior emulator run: CTC p50 646 ms, 5%
deadline timeouts, fused_swipe p95 178 ms); **B** leave the matrix at 2/3 until a real low-RAM
device/image exists; **C** build a product low-RAM AOSP image (multi-day project).

Leg commands once decided (run-id and corpus sizing per option):

```sh
# regenerate pooled file (also used in §5):
cat build/device-evidence/stock-hw-shard0-1.jsonl \
    build/device-evidence/grapheneos-hw-shard1-1.jsonl \
    build/device-evidence/lowram-emu-shard2-1.jsonl > build/device-evidence/phase0-matrix-partial.jsonl

# full low-RAM leg (driver merges the third environment into the shared metadata):
python3 tools/run_phase0_measurement.py --serial emulator-5554 \
  --corpus build/evaluation-data/combined-tap-v2/test.jsonl \
  --swipe-corpus build/model-data/swipe-latin-v1/test.jsonl \
  --model-dir build/linux-exports/context-shared-a/export \
  --swipe-model build/linux-exports/swipe-a/export/swipe-latin-v1.onnx \
  --artifact-pin docs/phase-0-artifact-pin.json \
  --core-apk-sha256 8b8eb8644ffe309ef007ea3685cd61e8cfa2d3c695fc24c2c7df1f2917a28f4c \
  --app-commit 4d1c990e727c78cf6e74497bb8c414fc8dda978d \
  --run-id lowram-emu-shard2-1 --environment low_ram_emulator \
  --shard-count 3 --shard-index 2 --instrument-timeout 43200 \
  --output build/device-evidence/lowram-emu-shard2-1.jsonl \
  --metadata build/device-evidence/phase0-matrix-v1.metadata.json

# pooled evaluation once all three environments exist:
python3 tools/evaluate_engine.py build/device-evidence/phase0-matrix-partial.jsonl \
  --metadata build/device-evidence/phase0-matrix-v1.metadata.json \
  --report build/reports/phase0-matrix-v1.report.json
```

**Sharding gotcha learned today:** the instrumentation applies the `--shard-index/-count` filter to
the corpus file *as pushed*. Pre-truncating a pre-sharded file gets filtered a second time
(that is how the GrapheneOS leg measured 100 of 300 planned swipe rows — exactly the evaluator's
per-environment minimum, so it stands, but plan file sizes accordingly: to measure N rows of a
shard via a prepared file, include 3·N rows of that shard in the file).
